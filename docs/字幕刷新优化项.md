# 字幕刷新逻辑：现状分析与优化项

> 目标约束（用户原话）：**可以缓刷新，但要看得懂。**
> 本文把这句话翻译成可验收的规则，逐条对照本仓库现状，再给出可落地的优化项与验收标准。
>
> 证据分级：✅ = 本仓库代码/实测（Lead 跑的临时诊断，已删除）；📖 = 外部来源（URL 见 §7）；
> ⚠️ = 未验证/不确定（§8）。
> 调研分工：ASR/时序侧与渲染侧各由一名独立调研员完成，关键引用由 Lead 抽查复核（§7 标注）。

## 0. 结论摘要（TL;DR）

当前刷新链路**不是"刷新太慢"，而是"刷新看不见"**：节流与动画做得不少，但有三处结构性问题让字幕读不懂：

| # | 问题 | 一句话 | 证据 |
|---|---|---|---|
| **A** | **长句尾巴永不显示** | `renderText` 用 `.prefix(maxLines)`，105 字中文只显示前 60 字，**后 45 字从头到尾没上过屏** | ✅ 实测（§3.1） |
| **B** | **最短停留与阅读速度无关** | 固定 1.5s；按 Netflix 成人 20 CPS，42 字需 2.1s、60 字需 3.0s → 长句必然没读完就被顶掉 | ✅ 算术 + 📖 |
| **C** | **排队"后到顶替"会整句丢失** | `renderSentenceWithMinDisplay` 取消上一个待渲染句 → 那句话**一次都没显示**（翻译却照发） | ✅ 代码 |

另外两条"缓刷新过头"的：

| # | 问题 | 一句话 |
|---|---|---|
| **D** | 逐字入场动画总时长失控 | stagger 45ms/字 + 320ms：30 字块要 **1.67s** 才全部可见，慢于语音节奏 |
| **E** | 已显示文本会被回改 | ASR 每轮重转写未封口 tail，中间一个词变了就整段重画（`SplitSubtitleText` 在变化点之后全部重播动画） |

**建议的优化顺序**：A + B + C 一起做（互为前提，见 §5.0）→ D + E（刷新质量）→ 布局/动效/无障碍（F–J）。

**外部成熟做法**（详见 §4）：LocalAgreement-2 提交（whisper_streaming）、稳定前缀只增不减（Chromium `GreedyTextStabilizer`）、固定 2 行底部锚定滚动窗口（WebVTT `scroll:up` / CEA-608 RU2 / Chromium Live Caption 48dip）、以及 Netflix/BBC 的字幕时长与阅读速度规范。

> **修复状态**：A/B/C/D/E/F/H 已落地（实现见 §9，含每条验收方式与"未能验证"的部分）；G/I/J 见 §9.3 的取舍说明。
> 本文正文保留**修复前**的现状描述与证据，作为回归依据。

## 1. 「看得懂」= 五条可验收的红线

把用户的约束落成规则，后面所有优化项都对着这五条验收：

| 红线 | 规则 | 为什么（出处） |
|---|---|---|
| **R1 不丢尾** | 屏幕上必须能看到**最新**的话；任何时刻被隐藏的只能是更早的内容 | 直播字幕的价值在于"现在在说什么"；CEA-608/WebVTT 滚动窗口都是"最旧行滚出" |
| **R2 不回改** | 已经显示过的文字不得被静默替换/删除（除非整句被 ASR 修正且用可感知的方式标注） | BBC §21.4 要求改字必须显式标注；§21.5 明确禁止"每出现新词整行水平移动" 📖 |
| **R3 够读** | 每屏停留时长 ≥ 该屏字符数 ÷ 阅读速度（成人 20 CPS、儿童 17 CPS） | Netflix I.14/I.1（最短 5/6s、最长 7s）📖 已复核 |
| **R4 不跳重心** | 行数变化（1↔2 行）不得让文字块整体上下/左右跳动 | Chromium Live Caption 固定 2 行、行高恒定（具体 dip 数值 ⚠️ 未独立复核，见 §8.2）；WebVTT region 高度 = `lines × 6vh` 📖 |
| **R5 动效有预算** | 一次刷新引入的动画总时长 ≤ 250ms，且不改变文字位置 | HIG 明确"避免 blur 进出动画""位移改 fade"；Chromium 对文本本身**不做过渡** 📖 |

**允许的"缓"**（用户已授权）：只显示已提交前缀、新字最多滞后 1 个 ASR chunk、行级替换等到句边界。
**不允许的"缓"**：R1–R5 任何一条被破坏。

## 2. 现状：刷新链路全景

```
音频 ──▶ ASRManager 活循环（重转写未封口 tail，250ms/500ms/1000ms 轮询）
        └─▶ AppState.liveSegments（末段=interim，其余=final）
             └─▶ FloatingLetterOverlayBinder.pushState（SubtitleUpdateScheduler 150ms 批处理）
                  └─▶ FloatingLetterViewModel.updateSubtitleState（输入签名幂等门）
                       ├─ SpeechEndpointDetector（标点/长度断句）
                       ├─ SubtitleSentenceTrigger（是否新句）
                       ├─ SubtitleDeduplicator（8s 窗口 suppress/merge/refresh）
                       ├─ renderText / renderTranslation（断行 + .prefix(maxLines)）
                       └─ 最短停留队列（1.5s，后到顶替）
                            └─▶ FloatingLetterViews.SubtitleTextLayerView
                                 └─ SplitSubtitleText（末行逐字入场 diff）
```

## 3. 问题清单

### 3.1 A：长句尾巴被 `prefix(maxLines)` 截掉（P0，违反 R1）

**代码**：[renderText:893](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViewModel.swift:893>) `Array(splitter.split(text, …).prefix(limit))`；
[renderTranslation:920](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViewModel.swift:920>) `Array(lines.prefix(limit))`；
[SubtitleRenderer.setLines:484](<Sources/Pipeline/Subtitle/FloatingLetter/SubtitleLayers.swift:484>) 又 `prefix(maxLines)` 一次。

**✅ 实测**（临时诊断测试，跑完已删）：

```
【中文】原文 105 字 → split 出 4 块（各 [30, 30, 30, 15] 字）
【中文】prefix(2) 显示 60 字，被丢弃 45 字        ← 43% 的内容从未上屏
【中文】显示的末 12 字：…段连续的中文测试语音内容
【中文】被丢弃的开头 12 字：这是一段连续的中文测试语…
【英文】原文 258 字符 → split 出 4 块（各 [78, 77, 72, 28] 字符）
【英文】prefix(2) 显示 155 字符，被丢弃 100 字符
【对照】未接线的 SubtitleSplitter.split（suffix）保留末尾：[26, 1] 字
```

**为什么发生**：whisper 的 interim 是"整个 chunk 的重转写文本"，一次可能就是几十上百字；断行把它切成多块后，`prefix` 保留**最早**的两块。

**影响**：用户读到的是句子开头，正在说的话（尾巴）永远看不见——这是"看不懂"的第一杀手，且与节流无关，做再多平滑都没用。

**注意**：仓库里还有一个**未被接线**的 [`SubtitleSplitter`](<Sources/Pipeline/Subtitle/FloatingLetter/SubtitleLayers.swift:205>)，语义恰好相反（`.suffix(maxLines)`，保留末尾），其注释也自认"两套断行规则并存"。接线时二选一。

---

### 3.2 B：最短停留是固定值，不按阅读速度算（P0，违反 R3）

**代码**：`minSentenceDisplay = 1.5`（[:775](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViewModel.swift:775>)）。

**✅ 算术**（Netflix 成人 20 CPS）：

```
42 字 @20CPS → 需 2.10s；最短停留 1.5s → 不够，差 0.60s
60 字 @20CPS → 需 3.00s；不够，差 1.50s
84 字 @20CPS → 需 4.20s；不够，差 2.70s   ← 2 行 × 42 字符（Netflix 上限）
```

**📖 规范**：Netflix 最短 5/6s、最长 7s、成人 20 CPS、42 字符/行、最多 2 行；BBC 0.3s/词（160–180 wpm）、≤37 字符、横屏 2 行。

**影响**：长句（尤其翻译后变长的中文→英文）读不完就被下一句顶掉。

**与 A 的关系**：只改 B 不改 A，会让"看不见的尾巴"占屏更久；只改 A 不改 B，则滚得快到来不及读。**必须一起改**。

---

### 3.3 C：排队"后到顶替"导致整句丢失（P0，违反 R1）

**代码**：[renderSentenceWithMinDisplay:779](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViewModel.swift:779>) 每次 `pendingSentenceTask?.cancel()` —— 正在排队的句子被新句顶掉，**永远不会上屏**；但 `onSentenceCompleted` 已经发出（翻译照做），所以历史里有、屏幕上没有。

**影响**：快语速/短句连发时，用户会"漏句"。

**外部对照**：CEA-608 roll-up（RU2/RU3/RU4）与 WebVTT `scroll:up` 都是**滚动**而非替换——旧行上移而不是消失；BBC 直播字幕明确要求"Two-lines of scrolling text"。

---

### 3.4 D：逐字入场动画总时长失控（P1，违反 R5）

**代码**：[FloatingLetterViews.swift:261-262](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViews.swift:261>) `staggerDelay: 0.045, duration: 0.32`；实现见 [SplitSubtitleText.swift:89-98](<Sources/Pipeline/Subtitle/SplitSubtitleText.swift:89>)（`delay = (index - commonPrefix) * stagger`）。

**算术**：一个 30 字的新块 → 末字 **1.35s 后**才开始入场、**1.67s 后**才完全不透明；而下一个 chunk 0.25–1s 后就到 → 动画持续被打断/叠加，屏幕长期处于"半透明过渡态"。

**📖 外部**：Chromium Live Caption 对文本本身**不做过渡**（靠稳定前缀 + 按行截断）；Apple HIG 明确反对 blur 进出动画、建议位移改 fade；WebVTT 规范里唯一的滚动过渡常数是 **433ms**。
**仓库里的 `SubtitleBlurText`**（blur 10→5→0、y −50→5→0、stagger 0.12s）目前只用在 `DebugSubtitleView`，**没进生产路径**——接线前请先按 R5 收敛参数。

---

### 3.5 E：已显示文本被回改（P1，违反 R2）

**机制**：ASR 活循环每轮**重转写未封口 tail** 并整体替换（[ASRManager.swift:282-301](<Sources/Pipeline/ASR/ASRManager.swift:282>)）；`SubtitleDeduplicator` 只能挡住"完全相同 / 短前缀"（[:396-414](<Sources/Pipeline/Subtitle/FloatingLetter/SubtitleLayers.swift:396>)），中间一个词变了就整段变化；`SplitSubtitleText` 的公共前缀 diff 在变化点之后**全部重播动画**（[SplitSubtitleText.swift:108-124](<Sources/Pipeline/Subtitle/SplitSubtitleText.swift:108>)）。

**📖 成熟做法**：
- whisper_streaming 的 `HypothesisBuffer.flush()` —— 源码注释原文 *"returns commited chunk = the longest common prefix of 2 last inserts"*；`insert()` 用 0.1s 时间容差、1s 重对齐、1–5 词重叠去重（✅ 已复核源码）。
- WhisperLive：同一输出重复 N 次（默认 10，faster-whisper 7）才提交。
- Chromium `GreedyTextStabilizer`：位置直方图取众数 + 阈值，**稳定前缀只增不减**（"prevents shrinkage"）。
- Apple SpeechTranscriber：`volatileRange` 之外的文本"不会被替换"，可安全 consolidate；但 volatile 结果**会**替换旧结果，且 `isFinal=false` 不保证再收到 final 版。
- WhisperLiveKit 在 whisper_streaming 基础上补了 **>15s 无提交则 reset buffer**（防冻结），原版没有。

---

### 3.6 F：文本区布局随行数变化跳重心（P1，违反 R4）

**代码**：[FloatingLetterViews.swift:248-296](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViews.swift:248>)：`Spacer(minLength: 0)` 上下夹 + `.frame(maxWidth: .infinity, maxHeight: .infinity)`；行数 1↔2 切换时整块文字上下移动，而 [renderText:895](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViewModel.swift:895>) 还给这个位移**加了 180ms 动画**（把跳动变得"看得见"）。

**📖 外部**：Chromium Live Caption 固定 2 行窗口（具体 dip 数值 ⚠️ 未独立复核，见 §8.2）；WebVTT region 高度 = `lines × 6vh`；CEA-608 底部锚定 `base_row`。

---

### 3.7 G：居中排版导致"每加一字整行横移"（P2，违反 R2）

**代码**：`SplitSubtitleText` 用 `SubtitleFlowLayout` + `.frame(maxWidth: .infinity, alignment:)` 按内容宽度居中（[SplitSubtitleText.swift:75-102](<Sources/Pipeline/Subtitle/SplitSubtitleText.swift:75>)）。
**📖 BBC §21.5** 点名禁止"每个新词导致整行水平移动"；BBC 直播字幕要求**左对齐**。
**现状缓解**：App 默认 `subtitleHorizontalAlignment = "left"`（[AppState.swift:118](<Sources/App/AppState.swift:118>)），所以只有用户手动选居中才会踩到——建议在设置页对"居中"加一句说明，或对居中模式锁定已提交前缀的排版。

---

### 3.8 H：字幕路径未接 Reduce Motion（P2）

**证据**：`Sources/Pipeline/Subtitle/**` 下 `reduceMotion` **0 命中**；已接的只有 [PermissionGuidePanel.swift:82](<Sources/App/PermissionGuidePanel.swift:82>)、[ProgressViews.swift:44](<Sources/App/Workbench/ProgressViews.swift:44>)、[ContentView.swift:128](<Sources/App/ContentView.swift:128>)（`.reduceMotionGate()`）。字幕动画全部直接 `withAnimation` / `Animation`，绕过了 [DesignTokens.swift:110](<Sources/App/DesignTokens.swift:110>) 的 `Motion.anim` 闸门。
**📖**：HIG Motion 五条 + WCAG 2.3.3。

---

### 3.9 I：背景透明度 0.4 落在 macOS "淡影"区间（P2）

**代码**：`subtitleBackgroundOpacity` 默认 **0.4**（[AppState.swift:136](<Sources/App/AppState.swift:136>)）。
**📖**：Chromium 源码注释指出 alpha < 90% 时窗口背景会残留"淡影"（ghost）；建议要么 ≥0.9（实底），要么 ≤0.35（明确半透），避免中间值。

---

### 3.10 J：没有"看得懂"的可测指标（P2）

现状只有"端到端延迟"（延迟条）与 `SubtitleLatencyManager` 的 lastTranslationMs/lastDisplayMs，**没有**：擦除次数、每句可见时长、实际 CPS、尾巴是否上屏。
**📖 Chromium** 把抖动做成指标：`flicker_rate = erasure_count / partial_result_count`（建议照搬）。

**两个常见误引（调研员主动纠偏，值得记下）**：
1. **WebVTT 规范里没有 pop-on / paint-on / roll-up 这三个词**——它们出自 CEA-608；WebVTT 只有 region `scroll:up`。
2. **WCAG 2.2 不含任何 CPS / 最短时长数字**（1.2.4 只要求"提供字幕"）；CPS 数值来自 Netflix/BBC 这类行业规范，引用时别挂在 WCAG 名下。
3. `jianfch/stable-ts` **没有 `stabilize` API**（其 `stabilization/` 子包是静音抑制）；它解决的是时间戳对齐，**不是** partial 抖动——别把它当作抖动方案引用。

## 5. 优化项（按优先级）

### 5.0 为什么 A/B/C 必须同批做

- 只修 A（改滚尾）：长句尾巴终于可见，但仍按 1.5s 顶掉 → 读不完。
- 只修 B（按 CPS 延长）：屏幕上停留更久，但**尾巴仍然看不见** → 读的是过期内容。
- 只修 C（不丢句）：队列变长 → 显示进一步滞后。

三者共同指向一个模型：**固定 N 行滚动窗口 + 提交前缀冻结 + 按阅读速度决定滚动时机**。这正是 CEA-608 roll-up / WebVTT `scroll:up` / Chromium Live Caption 的做法。

---

### P0-1（A）改成滚动窗口：只保留最新 N 行

- **改法**：`renderText`/`renderTranslation` 的 `.prefix(limit)` → **`.suffix(limit)`**；并让 [`SubtitleRenderer.setLines`](<Sources/Pipeline/Subtitle/FloatingLetter/SubtitleLayers.swift:483>) 承担唯一的截断职责（去掉双重 prefix）。
- **同时清理双实现**：把未接线的 [`SubtitleSplitter`](<Sources/Pipeline/Subtitle/FloatingLetter/SubtitleLayers.swift:205>)（本来就是 suffix 语义）定为唯一断行实现，`SubtitleSentenceSplitter` 退化为它的参数化封装或直接删除，避免"两套断行规则"。
- **验收**：新单测 —— 渲染 105 字中文后，屏幕文本的最后 30 字必须等于输入文本的最后 30 字；且总显示字符数 ≤ `maxLines × 30`。
- **风险**：低（纯函数级改动，有既有 `SubtitleSplitterTests` 13 个用例兜底）。

### P0-2（B）最短停留按阅读速度计算

- **改法**：`minDisplay = clamp(chars / cps, floor, cap)`，取 `cps = 20`（成人）/`17`（儿童），`floor = 5/6s`（Netflix 单条最短），`cap = 7s`（Netflix 上限）；字符数取"当前屏可见字符数"（`renderer.lines.joined().count`）。
- **配套**：`maxSentenceLength` 从中文 28 / 其他 70 收到与"2 行 × 42 字符"匹配（中文 ~42、西文 ~84），避免单句天然超过阅读预算。
- **验收**：单测 —— 42 字 → ≥2.1s；10 字 → ≥5/6s（下限）；84 字 → ≥4.2s 且 ≤7s。
- **风险**：中——显示变慢会积压；必须与 P0-3 的"不丢句"一起上。

### P0-3（C）不丢句：滚动而不是顶替

- **改法**：`pendingSentenceTask` 的"后到顶替"改为**滚动模型**：新句进入窗口底部、旧句上移一行；队列上限 2 屏，超出时**合并**进当前屏（而不是丢弃）。保留"最短停留"作为**滚动节拍**而不是"丢弃条件"。
- **验收**：单测/集成 —— 每 0.5s 连说 5 句，5 句都必须至少完整出现过一次（可用可注入的时钟把 1.5s 压缩）。
- **风险**：中——需要把 `renderSentenceWithMinDisplay` 从"任务取消"改为"状态机"，建议顺带把它抽成**纯策略类型**（如 `SubtitleDisplayPolicy`）以便单测（当前 ViewModel 无单测，策略外提后可测）。

### P1-1（D）动画预算封顶：新字只做纯淡入

- **改法**：`staggerDelay` → 0（或 ≤30ms）；`duration` → ≤120ms；**去掉 y 位移与 scale**（`fromOffsetY`/`fromScale` 置 0/1）；总预算 ≤250ms；`SubtitleBlurText` 若接线，blur 与位移必须去掉（HIG 反对项）。
- **验收**：输入 30 字新块，全部字符 ≤250ms 内可见（可用 `ImageRenderer` 时间序列或埋点断言）。
- **风险**：低——观感变化明显，建议加设置项"字幕动效：无/淡入/逐字"。

### P1-2（E）提交前缀冻结：LocalAgreement-2 + 尾部 holdback

- **改法**（低风险起步，**不需要**先开 token timestamps）：
  1. 在字幕层保存"上一次假设"与"已提交前缀"；每次新假设与已提交前缀做**最长公共前缀**比较，**已提交前缀只增不减**；
  2. 尾部 **holdback 2 个单元**（词/字）不进显示，避免最后一个词反复改；
  3. **10–15s 无提交**强制提交一次（WhisperLiveKit 的防冻结）；
  4. 换会话/封口时清空假设缓存。
- **验收**：新增可测指标 `flicker_rate = 擦除次数 / partial 次数`（Chromium 口径），同句增长期间必须为 **0**；单测：构造两次假设（人为改中间一个词）→ 显示文本只增长不回退。
- **风险**：中——会引入约 1 个 chunk 的额外显示滞后，但换掉的是"回改"这一最伤可读性的行为；符合用户"可以缓"的授权。

### P1-3（F）固定行盒布局：行高恒定 + 底边锚定

- **改法**：字幕文本区改为固定高度容器（`maxLines × lineHeight`，对齐 Chromium 48dip 思路），行高恒定、**底边锚定**，文字在其中滚动；行数变化**不加**整体位移动画（[renderText:895](<Sources/Pipeline/Subtitle/FloatingLetter/FloatingLetterViewModel.swift:895>) 的 `withAnimation` 去掉）。
- **验收**：连续 1 行 → 2 行 → 1 行，首行基线 y 坐标不变。
- **风险**：低-中（纯视图层）。

### P1-4（§3.5 配套）翻译只吃已提交源文 + 译文独立窗口

- **改法**：`onSentenceCompleted` 只在**句边界/已提交**时触发（现在 detector 的长度兜底也会成句，导致同一段话多次成句、译文互相作废）；译文窗口独立、只追加不回退；行级替换只在句边界发生。
- **参考**：WhisperLiveKit 的 AlignAtt + `--translate-on-complete`；obs-localvocal 的译文独立滚动窗口（1000ms）。
- **验收**：人为让源文回改一次 → 译文行不闪回、不清空。

### P2-1（G）左对齐/锁定原点

- **改法**：设置页"居中"模式下，对**已提交前缀**锁定排版（新字不改变已有文字的 x 位置）；或在文档/提示中明确"直播字幕建议左对齐"（BBC）。
- **验收**：居中对齐下追加 10 个字，已显示字符的 x 坐标不变。

### P2-2（H）接 Reduce Motion

- **改法**：字幕动画统一走 `Motion.anim(...)`（[DesignTokens.swift:110](<Sources/App/DesignTokens.swift:110>)）或读 `@Environment(\.accessibilityReduceMotion)`；reduce 时全部瞬时、无位移/缩放/blur。
- **验收**：系统开启"减少动态效果"后，字幕刷新无任何位移/缩放/blur（可用渲染快照对比）。

### P2-3（I）背景透明度避开"淡影"区间

- **改法**：默认 0.4 → 0.9（实底）或 0.3（明确半透）；设置页滑杆标注两档建议值。
- **验收**：目视 + 截图确认无残影；默认值改动需在 CHANGELOG/设置页提示。

### P2-4（J）把"看得懂"变成可观测指标

- **改法**：新增轻量埋点（复用 `PipelineLatencyStore` 的窗口均值模式）：`flicker_rate`、每句可见时长、实际 CPS、尾巴可见性、被顶替句数；状态页的延迟条旁边加一行"字幕可读性"。
- **验收**：目标值 —— `flicker_rate < 0.05`、每句可见时长 ≥ `chars / 20`、被顶替句数 = 0。

## 8. 未验证 / 不确定（不要当结论用）

1. **YouTube 自动字幕的滚动行为**：无官方渲染说明、播放器不开源 → 调研员未找到可靠一手来源；本文用 BBC + Chromium + CEA-608 作为等价依据。
2. **Chromium Live Caption 的具体布局常数**（`kNumLinesCollapsed=2`、`kLineHeightDip=24`、折叠容器 48dip、字号 16px、宽 ≤536dip）：来自调研员，Lead 在 `components/live_caption/` 下**未能定位**这些常量（该目录只列出 `caption_util.*` 等文件），故标 ⚠️；`GreedyTextStabilizer` 的机制与 `min_token_frequency_` 默认值 0 **已复核**（`greedy_text_stabilizer.cc`）。布局建议本身由 WebVTT region 高度与 CEA-608 底部锚定独立支撑，不依赖这组数字。
3. **Chromium `GreedyTextStabilizer` 的生产 `min_token_frequency` 实参**：源码里是构造参数（默认 0 = 输入即输出），未找到生产调用点的具体数值 → 实现时按"稳定前缀只增不减"的语义做，不要照抄数字。
4. **WebVTT `lines` 的默认值**：规范正文未给，`vtt.js` 实现默认 3。
5. **BBC 指南原文**：本环境直连失败，取自 2024 Wayback 快照；若需引用具体条款号，建议在可直连网络复核一次。
6. **浅色模式/真实观感**：本文所有可读性结论基于数值与代码，未做真机长时间跟读测试（建议第 1 批落地后做一次 30 分钟真实会议跟读，记录"漏读/误读"次数）。
7. **环境限制**：本次调研中 `web_search` 工具因 HTTP 402（余额不足）不可用，所有外部结论均由调研员用 `curl`/`web_fetch` 直取一手页面与源码；这意味着**无法做广度发现**，只能沿已知 URL 深挖——若有冷门实现值得对比，建议先恢复搜索通道。

### 9.5 复查发现与返修（可追溯）

| 复查发现 | 返修 |
|---|---|
| **task-7｜R2 主路径被破坏**：中段改一个字 → 画面 12 字立即缩到 2 字（4 个反例 + 1 个对照组） | ① `LocalAgreementStabilizer` 分叉时**不再回退** `committed`；零公共前缀=换段立即提交、有公共前缀的中段改写持续 **1.5s** 才采信；② `SubtitleDisplayGate` 新增"候选是当前画面真前缀（缩回）→ 一律持有、**1.0s** 后接受"；③ 新增回归测试把 4 个反例钉住 |
| **task-7｜队列容量溢出丢弃**最旧句（6 句/0.35s 场景第 2 句一次没上屏） | 改为**合并**：`SubtitleSentenceQueue.merged` + `replaceFirst`；指标 `droppedSentences`/`supersededSentences`（后者恒 0 是死字段）→ `mergedSentences` |
| **task-7｜`maxLines=3` 译文被裁**（超出默认容器 200pt） | 模型层兜底：`AppState.requiredSubtitleContainerHeight(...)` + 行数/字号/行距变化与启动时抬高容器（只抬不降） |
| **task-7｜R3 口径不一致**（§1 写 5/6s，§5 写 0.8s） | `floorSeconds` 统一为 **5/6s** |
| **task-8｜分叉计时未随收敛撤销**（保护窗口实际是"距**首次**分叉 1.5s"，抖动输入下画面倒向少数派假设） | `h.hasPrefix(committed)` 分支**入口无条件**清计时；把复查者的最小复现写成回归测试 `testReconvergingHypothesisCancelsTheDivergenceTimer` |
| **task-8｜容器下限算小**（`S+T+16` vs 真实 `S+2T`：原文盒在容器里居中 + 译文 overlay 挂盒底） | 公式改为 **`S + 2T`**（rows=2 → 192、rows=3 → 288）；抬高入口补齐到两个字号 setter 与行距 setter |
| **task-8｜合并只是记账**（长句积压时被合并句仍看不到开头；且合并文本无上限，20 句可涨到 126 字） | 合并文本加 **120 字上限**（保留末尾）+ 测试；文档写明"合并只在合并文本 ≤ 2 行窗口时让两句都可见" |

**已知取舍（非缺陷）**：
- 窗口拖拽到极小不自动抬高容器（`onContainerResized` 不触发）——那是用户主动选的大小，自动抬会跟拖拽打架；底部锚定的滚动窗口保证**最新行**仍可见。
  - 复查者补充的事实：窗口 `minSize.height = 172`（`FloatingLetterOverlayController.swift:688`）**小于 2 行所需的 192pt**，所以拖到最小仍会裁掉译文底部；但底部锚定的原文盒在 172pt 下仍完整（rows=3 时 S+16=130 < 172），"最新行可见"（R1）成立。
  - 口径：**拖小仅当次有效**——`init()` 与行数/字号/行距 4 个 setter 会把高度抬回下限并持久化。若要让"用户主动拖小"长期生效，需要加 `userOverrodeHeight` 标志（未做，属后续项）。
- 合并文本超过 2 行窗口时只有尾巴可见——这是 2 行滚动窗口的固有上限（R1 优先：最新内容必须可见）。短句积压时两句都完整可见（复查实测：短句 12 字帧长 `[12,24,12,12,12]`，两句头尾都在）。

### 9.3 未做 / 取舍（诚实清单）

1. **G 居中排版锁定原点**：未改。App 默认 `subtitleHorizontalAlignment = "left"`，只有用户手动选居中才会踩到 BBC §21.5 的问题；锁定原点需要改布局引擎，收益/风险不划算 → 保留为后续项。
2. **I 背景透明度 0.4**：**刻意不改**。证据只是一条 Chromium 源码注释（且可能平台相关），拿它改一个用户可见的默认值不划算；建议后续用真机对比再定。
3. **J 的状态页展示**：只做了埋点 + 日志，没接状态页 UI（避免与延迟条那套 `PipelineLatencyStore` 混淆）。建议后续把 `flicker_rate` / 每句可见时长 / 实际 CPS 做成"字幕可读性"一行。
4. **滚动窗口的"顶部行原地换字"**：`ForEach(id: \.offset)` + tail 窗口下，滚出的一行是**原地换字**（硬切）而不是滚动动画。本轮选择"零位移"（不跳），带滚动的 roll-up（WebVTT 规范 433ms 上滚）留作后续项。
5. **`SubtitleSplitter` 双实现**：保留未删（它是死代码但被 13 个测试覆盖，删除要改测试而功能无收益）。真正的隐患（prefix/suffix 语义相反）已由本轮统一到 tail 消除。
6. **`SubtitleBlurText` 的位移/blur**：只被 `DebugSubtitleView` 使用，不在生产路径 → 未动。
